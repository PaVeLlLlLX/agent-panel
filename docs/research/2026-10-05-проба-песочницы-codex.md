# Проба песочницы Codex для проверок рецензентов (ступень 0)

05.10.2026, Windows 10, `codex-cli 0.159.0-alpha.12.1` из расширения ChatGPT
26.930.21537, песочница **unelevated** (`[windows] sandbox = "unelevated"` в
`~/.codex/config.toml`; файл не менялся). Скрипт — `scripts/codex-sandbox-probe.mjs`,
сырые ответы — в локальной папке SDD (`probe/*.json`, в git не входят).

Обозначения: `<папка>` — папка рецензента `%LOCALAPPDATA%\agent-panel\review\probe\codex\`
(создана до запуска, вместе с `tmp\`); `<проект>` — временная папка-проект
`%TEMP%\codex-sandbox-probe-<время>\project` с `marker.env` (`SECRET=probe`) и `code.py`.
Профиль — ровно из спецификации (ступень 2): `default_permissions: "agent-panel-review"`,
`filesystem: {":root": "read", "<папка>": "write"}`, `network.enabled: false`,
`shell_environment_policy.set` с `TEMP`/`TMP` = `<папка>\tmp`, `PYTHONDONTWRITEBYTECODE=1`,
`MPLCONFIGDIR`; `approvalPolicy: "never"`, поля `sandbox` нет; `initialize` с
`capabilities: {}`, как у панели.

Ветка пробы — новая (`01a10b6c…`); чат владельца не продолжался. Модель — по
умолчанию из каталога (`gpt-6.1-sol`), уровень `low`. Ходов модели — **четыре**
(предел задачи — 3–4); недельное окно Codex показывало 11% на всех четырёх.
Временная папка-проект и `review\probe` удалены (`--cleanup`); фоновые python пробы
сняты; усиленная песочница не трогалась.

## Отклонения от плана

- **Адрес для сырого сокета.** `93.184.215.14:80` не отвечает и без песочницы
  (тайм-аут с машины). Скрипт проверяет адрес из плана, иначе берёт адрес
  `example.com` из DNS, ответивший без песочницы (`104.20.23.154`).
- **Шесть проверок шага 2 повторены в ходе шага 3.** С `cwd` = проект модель не
  запустила ни одной команды (раздел выше), поэтому продолжение с `config` шло с
  `cwd` = `<папка>`, и в тот же ход вошли шесть проверок вместе с `c.txt`/`d.txt`
  (`--resume --cwd folder --checks`) — без лишнего хода. Продолжение без `config` — тоже
  с `cwd` = `<папка>`.
- **Четвёртый ход** (`--python`): окружение, `.venv`, импорт кода и `tempfile` под
  профилем в ходе модели — п. (д) и п. 4 «Пробы» спецификации; в плане `.venv`
  проверялся только через `command/exec`.
- **`command/exec` — шире плана:** строгая форма политики рядом с формой плана
  (см. выше, проект пробы лежит в `%TEMP%`), запись в `%TEMP%`, запуск без
  `sandboxPolicy`, окружение с `env` и без, `python` из `PATH`, импорт кода проекта,
  фоновый процесс. Первый прогон сохранён как `exec-first.json`; второй начинался с
  очистки следов первого.
- Модели велено писать файлы командой оболочки, а не инструментом правки: проверялась
  песочница ОС. Путь `apply_patch` под профилем не проверен.
- Фоновый процесс проверен и после остановки app-server, не только через 10 с.
- Уборка удалила и пустые `%LOCALAPPDATA%\agent-panel\review`, `%LOCALAPPDATA%\agent-panel`,
  созданные пробой.

## Не проверено

- `permissionProfile` в `command/exec` (экспериментальное API, профиль должен быть в
  конфигурации процесса через `-c`).
- `runtimeWorkspaceRoots` как способ оставить рабочей папкой проект.
- Загружает ли Codex `AGENTS.md` проекта, когда рабочая папка — `<папка>` (у проекта
  пробы `AGENTS.md` нет; `instructionSources` пуст в обоих случаях).
- Усиленная песочница (решение владельца).

## Решения для реализации

**(а) Профиль в `config` принимают и `thread/start`, и `thread/resume`** — без
`experimentalApi` и без поля `sandbox`. Но под unelevated команды под профилем
выполняются, **только если рабочая папка ветки — папка рецензента** (или лежит в
ней). С `cwd` = проект Codex отказывается запускать любую команду, включая чтение.
Отсюда для задач 7–9:
- ступень 1 (`sandbox: "read-only"`) — `cwd` = проект, как сейчас;
- ступень 2 — `cwd` = `<папка codex>`; абсолютный путь проекта — в роли; команды над
  репозиторием — с абсолютными путями (`rg … <проект>`, `git -C <проект> …`); роль
  велит сначала прочитать `<проект>\AGENTS.md` (сам Codex его, вероятно, не
  подхватит — не проверено);
- принятие профиля панель проверяет **по ответу** `thread/start`/`thread/resume`:
  `cwd` = папка, `sandbox.type === "workspaceWrite"`, `sandbox.networkAccess === false`,
  `sandbox.excludeTmpdirEnvVar === true`, в `sandbox.writableRoots` нет ничего, кроме
  папки, `activePermissionProfile?.id === "agent-panel-review"`. Любое расхождение —
  перезапуск ветки «только чтение» (ступень 1) и строка в ленте. `command/exec` этот
  отказ не ловит: он проверяет политику процесса, а не связку «профиль + рабочая
  папка ветки».

**(б) Профиль не сохраняется при продолжении.** `thread/resume` без `config` вернул
`readOnly` и `activePermissionProfile: null`. Передавать `config` при **каждом**
`thread/resume` (и при перезапуске после сбоя, и при смене модели). Пропуск безопасен
(откат в «только чтение» по `config.toml` владельца), но запись в папку пропадёт; та же
проверка ответа из (а) это покажет.

**(в) `command/exec` работает** с `cwd` = папка, но `sandboxPolicy` — только в строгой
форме:
`{type: "workspaceWrite", writableRoots: [<папка>], networkAccess: false, excludeTmpdirEnvVar: true, excludeSlashTmp: true}`.
Без флагов `exclude…` корнем записи становится `%TEMP%` пользователя (и всё, что в нём
лежит). `sandboxPolicy` передавать всегда (без него — политика из `config.toml`);
`env` — с `TEMP`/`TMP` = `<папка>\tmp`, `PYTHONDONTWRITEBYTECODE=1`, `MPLCONFIGDIR`
(`shell_environment_policy` к `command/exec` отношения не имеет). Самопроверка:
1. запись `<папка>\probe.txt` — ответ `{exitCode: 0}` и файл на диске;
2. запись в проект — **ошибка JSON-RPC** с «sandbox denied» и файла нет. Обычный
   ответ с `exitCode 0` здесь — провал самопроверки.

Исполнитель скриптов Gemini разбирает три исхода: ответ `{exitCode, stdout, stderr}`;
ошибку «sandbox denied exec error, exit code: N, stdout: …, stderr: …» (код и вывод — из
текста ошибки); ошибку «command timed out».

**(г) Превышение `timeoutMs`** — ошибка JSON-RPC `-32603` «exec failed: sandbox error:
command timed out», ровно по сроку; кода 192 и частичного вывода нет. Панель пишет
«превышено время» и не ждёт вывода.

**(д) Python из `.venv` под профилем работает** — и в ходе модели, и через
`command/exec`; `python` по имени тоже находится. Импорт кода проекта работает и не
оставляет `__pycache__` в проекте; `TEMP`/`TMP`/`MPLCONFIGDIR` из
`shell_environment_policy.set` доходят до команд модели, `tempfile` пишет в
`<папка>\tmp`.

**Ещё, для стоп-сигнала и гарантий (задачи 8, 9, 11, 12):**
- Сеть на unelevated не закрыта: `urllib` упирается в прокси, сырой сокет выходит.
  Чтение не ограничено: маркер прочитан. Это совпадает с «Гарантиями» спецификации.
- Фоновые процессы переживают и команду, и остановку app-server (`killTree` их не
  находит). После хода Codex и после прогона скриптов Gemini панели нужно самой искать
  процессы, в командной строке которых есть путь папки рецензента
  (`Win32_Process.CommandLine`), и снимать их; процесс без пути папки в командной строке
  так не найти — остаточный риск, правило «без фоновых процессов» в роли остаётся.
- Отклонённая песочницей команда модели приходит `commandExecution` со
  `status: "failed"` и `exitCode: 1` (не `declined`); команда, отвергнутая до запуска
  (несовместимый профиль), не приходит вовсе. `command` — строка вида
  `"C:\Program Files\PowerShell\7\pwsh.exe" -Command "…"`, `source: "unifiedExecStartup"`.
- Codex навсегда записывает папку в `~/.codex/cap_sid`; удаление папки снимает ACE,
  запись остаётся. Очистка папки командой владельца это учитывает: ничего в `~/.codex`
  панель не трогает.
